# 2026-06-15 — Latency overhaul: in-memory KB search SHIPPED + the full press-to-card roadmap

A big architecture + planning session. Turned the press-to-card latency problem from "the search is mysteriously 2.8s" into **one shipped fix (PR #17, merged + deploying)** plus a **hardened, sequenced roadmap** for the rest. Also uncovered a more important product bug than speed: the signal card can fire for the *previous* objection.

---

## 1. Diagnosed the latency root cause (the 2.8s "search")
Live gate test (real Zoom call) measured press-to-card at **1.9–4.9s**. Broke it down:
- **Search ~2.8s** — embedding (~0.5s OpenAI) + the Supabase `search_kb_by_trigger` RPC.
- **Generation ~1.4–1.9s** — Haiku writing the card (non-streaming).

`EXPLAIN ANALYZE` in Supabase = **2,091ms inside the DB**. Root cause: the RPC's `DISTINCT ON (e.id) … ORDER BY e.id, distance` shape **cannot use a vector index**, so every press seq-scans + de-TOASTs all 6,554 × 1536-dim vectors on a small shared instance. Not a missing index — the query shape structurally opts out of any index. (The 2026-04-17 junction-table work optimized match *quality*, never measured *speed*.)

## 2. In-memory KB search — BUILT, parity-gated, reviewed, MERGED (PR #17)
The fix top engineers use at this scale (6.5k vectors = 40MB): load the whole eligible KB into the **Railway server's memory** at boot and brute-force cosine **in-process (~10–20ms, exact)**. Supabase stays the system of record; this is a cache.
- New `src/lib/wingman/kb-memory-core.ts` (pure parse/normalize/pack/search) + `kb-memory.ts` (load/lifecycle/5-min staleness/atomic-swap/backoff retry/>25k alarm) + `src/instrumentation.ts` (boot load) + `knowledge-search.ts` (mem-first, **circuit-breaker-guarded** RPC fallback, `path=mem|rpc` log) + `pipeline-warmup.ts` (kick the load).
- **Parity gate (`scripts/test-kb-memory-parity.mjs`): 14/14 probes** match the live RPC — every shared similarity within **1e-4**, identical sets. The only diffs were exact-tie #1 reorderings (Issue #28/#29 duplicate triggers — multiple entries share "I need to think about it" so they score *identically*), correctly tolerated. **This proved the in-memory math is as good as the DB.**
- 20 new unit tests (59 total green); web + electron tsc clean; `wingman-reviewer` APPROVED with 2 should-fixes folded in (serve stale snapshot during a reload instead of dropping to RPC; 009 Stage-1 eligibility filter).
- **Live-verified:** `path=mem`, search `2,800ms → ~20ms`. **PR #17 merged → Railway auto-deploying.**

## 3. Migration 009 — fast fallback (run by Sebastian ✅)
`supabase/migrations/009_kb_trigger_hnsw.sql`: HNSW index + a **filter-then-rank** index-friendly rewrite of `search_kb_by_trigger` (same signature, backward-compatible). Makes the *fallback* fast too. EXPLAIN ANALYZE: **2,091ms → 330ms warm** (977ms cold first-run = index cache warming). The fallback is only hit in the seconds after a deploy before memory is ready.

## 4. Live test surfaced the real priorities
- **Search is solved.** Generation (Haiku ~1.5–2s) is now the #1 press-to-card cost. Embedding is ~0.2–0.5s (0ms when the 60s query cache hits).
- **THE IMPORTANT BUG (Sebastian caught it):** the card sometimes fires for the *previous* objection. Root cause = **Recall/Deepgram transcript finalization lag (1–3s):** Deepgram waits for a pause to finalize a sentence, so when the rep presses ↑↑ immediately after the objection, that sentence **isn't in the buffer yet** → the distiller works off the prior objection. This is a *correctness* problem (wrong card → "this thing is trash"), worse than raw speed. NOT caused by PR #17 — pre-existing.

## 5. The press-to-card roadmap (researched + sequenced)
Agreed order of impact: **partials → streaming → self-host embeddings.**
1. **Partial transcripts** (next). Recall natively supports `transcript.partial_data` (interim words, ~hundreds of ms) + `prioritize_low_latency`. Cuts the 1–3s lag → ~0.3s. **Design:** finals stay the authoritative buffer; partials are a provisional live tail, reconciled when the final lands. The Groq distiller already normalizes messy partials before embedding (it's the error-correction layer) so objection *gist* detection is robust to the unstable last 1–2 words — BUT we **measure partial-vs-final churn on a real call before committing** (Groq can't recover a genuinely-wrong word like "custom"→"customers"; and a rep won't re-press a bad card, they'll think it's trash). Provider research: **stay on Deepgram** (lowest-latency streaming specialist, sub-300ms, sub-7% WER, already our provider, tunable) — **AssemblyAI** is the accuracy-leaning fallback if the measurement shows Deepgram churning; ElevenLabs Scribe (sub-150ms) too new to bet a core dependency on.
2. **Streaming card reveal** (PR 2, gated on a 1h Railway SSE-buffering spike). First words ~0.5–0.8s. Kills the perceived generation cost.
3. **Self-hosted embeddings** (last). Local BGE model via `fastembed` in-process → ~10–50ms, no OpenAI dependency, and a 384-dim model shrinks the in-memory KB ~4x. Full hardened plan in `tasks/plan-selfhost-embeddings.md` (plan-reviewer found 3 blockers + 5 majors, all folded in: silent space-mixing in the boot window + 60s cache, DIM-must-move-onto-the-snapshot, ingestion-must-dual-write-or-rollback-breaks, Railway-latency-unproven). **Requires re-embedding the whole KB + a per-objection quality gate.**

## 6. Decisions made (see Decisions Log)
- In-memory KB search over Pinecone (right scale).
- **Self-host embeddings over the cross-user cache** — the cache only pays off at scale (0 users today); build quality/speed now. Cache deferred to `_Inbox/Future Build - Cross-User Objection Cache.md`.
- **REJECTED: the "armed objection listener"** (rep arms a mode, Wingman auto-fires/pre-generates) — re-opens the Phase 1 autonomous-firing pivot, high cost, wrong-card risk.
- Sequencing: partials → streaming → self-host (embedding is the *3rd*-biggest lever post-PR-17, so it goes last).
