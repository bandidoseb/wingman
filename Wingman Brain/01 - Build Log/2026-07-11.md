- **🔴 Production auth-redirect bug FOUND + FIXED — [PR #43](https://github.com/bandidoseb/wingman/pull/43) → merged → Railway.** Surfaced when Sebastian tried to open `/changelog` on his phone: after Google login he landed on `https://localhost:8080/dashboard`. **Root cause (NOT Supabase config — that was correct):** on Railway the Next server runs behind a proxy, so `new URL(request.url).origin` inside a route handler returns the container's **internal** address (`http://localhost:8080`). `src/app/auth/callback/route.ts` used that origin to build its post-login redirect → stranded the user on localhost. **The `/dashboard` suffix was the tell** — Supabase's own fallback never adds a path; only our callback code does. **This has been broken on production web since launch for Google OAuth, magic links, password reset, and email confirmation** — unnoticed because day-to-day sign-in is the desktop app (password login, which redirects client-side via `window.location.href`).
  - **Fix:** new `src/lib/auth/public-origin.ts` → `getPublicOrigin(request)` prefers the proxy's `x-forwarded-host` / `x-forwarded-proto`, falls back to the raw request origin in local dev (standard Supabase-docs pattern). Both `auth/callback/route.ts` AND `auth/confirm/route.ts` use the shared helper.
  - **`wingman-reviewer` caught the sibling bug:** `auth/confirm/route.ts` had the identical internal-origin flaw → password-reset + email-confirmation links were also landing on localhost:8080. Fixed in the same PR. Also added: `?next=` sanitized to same-site paths only (blocks `//evil.com`) — defense-in-depth against open redirect.
  - **Verified:** with `x-forwarded-host: app.meetwingman.ai` both routes redirect to `https://app.meetwingman.ai/…`; without headers, local dev keeps `http://localhost:<port>` (Electron dev unaffected). Sebastian live-confirmed Google login now lands correctly on production.

## Decisions Made and Why

| Decision | Reason |
|----------|--------|
| Inject Sales DNA ALL-or-nothing (every question answered) | A lone field skews the card worse than no context — half a picture misleads more than none. Same helper gates the 1c Deploy gate → one definition of "briefed" |
| Sales DNA is "averages, not gospel" — a lens, never evidence | The #1 risk is the AI attributing saved offer facts to the live prospect. Zero-fabrication is the bar; the fence ships inside the block + adversarial eval traps enforce it |
| Client-pass + prompt-cache + warm-at-deploy over a hot-path DB read | Lowest latency, matches how `live_summary` already flows; caching cuts repeat cost ~90%; warming makes the first press fast |
| Ship gate = `test-belief-ladder` GREEN with Claude + GPT dual-judge | Sebastian's hard stop — no ship if the anti-fabrication gate isn't green; two judges so one model's blind spot can't pass a fabrication |
| Pull the NUMBER CONFIDENCE rule (3.6b) forward into 1b | The gate was deliberately RED demanding it; we edit that exact prompt anyway. A green gate is impossible without it |
| Syntax auto-detect runs in the POST-CALL job, not on page-load | Reps fill this at onboarding with 0 calls and won't revisit the Sales DNA page — a page-load suggestion would never fire (Sebastian's correction) |
| Atomic single-key RPC for the syntax write | Both post-call and the client save rewrite the whole sales_dna blob; `jsonb_set` guarded on `syntax='unsure'` eliminates the lost-update race (reviewer) |
| Don't split the ↓ Dig button (breadth vs depth) | Mid-call menu = robotic, adds friction when the rep is most stuck, collides with the compass. Threading + natural-transition is the right solve — captured for a future session |
