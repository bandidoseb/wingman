## 1. The safety gate that is not polish

`electron/main.ts` registers **bare arrow keys** as global shortcuts during a call — `Up` for the
whole call, `Left/Down/Right` while the compass is open, as direct picks during flow mode, and
after a close chip. `globalShortcut` fires **before** a focused textarea sees the key.

So a rep typing into a chat box mid-call who presses ↑ opens the compass, and the next arrow fires
a slot: **a billed Sonnet stream and a card on the HUD, in front of the prospect.**

The bar is therefore disabled whenever a call is live, starting, or awaiting its disposition. It
also resolves the z-fight with the Live Hub pill (`bottom:80px; left:32px`, always-on-top
`screen-saver` level, wins every stacking contest).

`callPhase: "idle" | "live" | "processing"` rather than a boolean, because `"processing"` can last
minutes and telling a rep staring at "Processing call…" that *"coaching chat pauses during a live
call"* is simply false.

## 2. Three `wingman-reviewer` rounds — 15 findings, all fixed

The reviewer found things typecheck and 296 tests could not. The two most expensive:

**Quota over-counted by 1, permanently, across UTC midnight.** `onQuotaReported()` ran *before*
`markSent()`. A send at 23:59:59 landing at 00:00:00 comes back `{used: 1, day: <new>}` →
`quotaReconcile` re-anchors → `markSent()` then adds a phantom `sent: 1` on top →
`max(serverLive, baseline+sent)` stays one ahead for the rest of the day and never self-corrects.
Fix: `markSent()` first, reconcile last. Same area, second bug: `quotaReconcile` re-anchored on
**any** day mismatch, so client-vs-server clock skew around midnight flapped the anchor and wiped
the day's sends. Now re-anchors **forwards only** (`YYYY-MM-DD` compares lexicographically).

**`pruneStore` could delete the conversation the rep was reading.** Active threads were exempt from
the 7-day TTL but **not** from the 30-thread cap. Resuming an old chat from History makes it active
*without* bumping `updatedAt` (deliberate — ordering means "last message", not "last opened"), so it
stays the oldest thing in the store. One more new conversation anywhere → sorted off the end →
deleted from state, from History, and from `localStorage` on the next save. Silent. Now exempt from
both, and the unit test that had **enshrined the lossy behaviour** was rewritten.

Others worth remembering:
- **The send button rendered enabled after a mid-flight scope switch** while `send()` silently
  returned at the `inFlightRef` guard. Enter did nothing, nothing cleared, nothing errored. `sending`
  is per-**bar**; the affordance had been gated on the visible thread.
- **A dive discarded the transcript the server had already read**, so the turn right after *"Read
  it."* could come back with `transcriptStatus: "unknown"` → the route tells the rep it can't pull
  the transcript up. One Sonnet call and one quota decrement to produce a self-contradiction.
  `transcriptRowsFromDive()` now salvages those rows (synthetic `id`/`call_id`, marked provisional
  so Flight Log still refetches the real ones).
- **`crypto.randomUUID()` needs a secure context and THROWS** otherwise — would have failed a send
  with zero feedback. Fallback added.
- The request body was built **outside** the `try` while `inFlightRef` was already set: a throw
  there stranded the ref forever — permanent dots, dead composer, reload-only recovery.

## 3. Bugs I caused (the useful section)

**Two of them were the same bug, twice, three hours apart** — and neither was caught by any gate.

**Both times: a save-to-`localStorage` effect running in the same commit as the restore effect,
before React had applied the restored value, writing empty over what it had just read.**

- First instance (single global thread): the save effect ran with the pre-restore value, removed the
  key it had just read, then rewrote it with a fresh `savedAt` — so the 24h TTL reset on every
  dashboard load and a stale thread could never expire. Fixed with a `lastPersistedRef` holding the
  exact restored array instance.
- Second instance (whole thread store, during the History rewrite): I reached for a **ref** for the
  `hydrated` flag. A ref is set synchronously, so it already reads `true` when the save effect runs —
  while `store` in that closure is still `EMPTY_STORE`. It would have wiped every saved conversation
  on load.

**The structural fix, and the rule worth keeping:** *a flag that must be observed by a later effect
in the SAME commit has to be **state**, not a ref.* `setHydrated(true)` batches into the same commit
as `setStore(restored)`, so the save effect's first effective run already sees the restored data.
A ref cannot express "not until React has applied this".

I found the first one by re-reading my own diff before handing it over; I found the second the same
way, after the reviewer had already approved the round. **Neither would have failed a test** —
`vitest` runs in `node` with no jsdom, so effect ordering is untestable here. Re-reading the diff is
the only thing that caught either.

**A third, smaller one:** I told Sebastian the branch had "four commits" when it had three. Corrected
in this log; the number matters because it is what he'd check against after a break.

## 5. Individual chats — Sebastian's decision, and the model change it forced

> *"does it make sense to have it all in one thread? I think it makes more sense to have individual
> chats."* — with a Granola screenshot of its chat list.

Offered three options; he chose **"History list over existing threads"** (localStorage, no schema
change) and **"finish the Coach bar first"** over shipping PR 4 and doing history later.

The model went from `Record<scopeKey, {messages, suggestion}>` to first-class threads:

```
ThreadStore = { threads: Record<threadId, Thread>, activeByScope: Record<scope, threadId> }
Thread      = { id, scope, messages, suggestion, updatedAt }
```

**The consequence that matters: "New chat" stopped destroying anything.** It clears the *active
pointer*, not the thread — so the previous conversation moves to History **and a reply still in
flight lands in the conversation that asked for it.** That let me delete the `threadGenRef`
generation counter added two reviews earlier: there is no longer an orphaned-reply case to guard
against. (The reviewer independently enumerated everything the guard protected and confirmed the
removal is safe — worth re-reading if this is ever revisited.)

Titles come from data we already have — the call's prospect name, or "All calls" — **never from a
model.** An AI title would be a second call per thread, for a label, that could be wrong about the
rep's own call.

Storage: new key `wingman_coach_threads` holds the whole store; the old `wingman_global_chat` single
thread is **migrated on first load** honouring its 24h expiry, so nobody loses the conversation they
had open. TTL 24h → 7 days, capped at 30 conversations × 40 messages.

## 6. Two deliberate departures from the plan, both documented in code

1. **A dive only takes scope when the call actually opened.** The plan said "fall back to scope-only".
   But a scope whose row can't be resolved is exactly `scopeMissing`, which disables the composer —
   the rep would land in a thread they cannot type in.
2. **"New chat" stays in scope.** The plan had it drop the dive override. Dropping it changes which
   conversation is visible, so New chat would have to clear the *landing* thread too — meaning
   "start over on this call" would silently wipe the global thread and its saved history. The chip's
   ✕ is the one, visible way out of a call scope. `coach-scope.ts` has no New-chat reducer, and a
   test asserts it stays that way.
